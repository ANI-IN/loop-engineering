# [Semantic Evaluation for Text-to-SQL with Distilled Test Suites](https://arxiv.org/abs/2010.02840) <!-- check-style: allow SC33 the source title is quoted as published -->

Reading time: about 45 minutes.
Source: Ruiqi Zhong et al., [Semantic Evaluation for Text-to-SQL with Distilled Test Suites](https://arxiv.org/abs/2010.02840), 2020-10-06.

> **Terms on this page**
>
> - **Gold SQL**: The query an analyst wrote by hand that gives the right answer.
> - **Grader**: A check that passes or fails one stage of a run and says why.

## Why it matters

The last demo of Section 2: Verification loop shows a Structured Query Language (SQL) answer that
passes every grader and still fails the gold check. This paper explains why the gold check runs on
two databases, not one. A wrong query can return the right rows on one database by coincidence,
and a right query can look different from the gold. Comparing results on several databases built
to tell them apart is how DataPilot's evaluator scores the benchmark.

## Three key ideas

1. **One database gives false positives.** "Single" denotation evaluation executes the predicted
   query on one database and compares results. "It might create false positives, where a
   semantically different prediction ... happens to have the same denotation as the gold, on a
   particular database." A green result on one database is not proof.

2. **String match gives false negatives.** "In contrast, exact string match might produce false
   negatives": a query that means the same as the gold but is written differently fails. That is
   why DataPilot never compares query text, and why the SQL text evaluator
   (`BUG_SQL_TEXT_EVAL`) is a planted bug.

3. **Build the databases to break near misses.** The method distills "a small test suite of
   databases that achieves high code coverage for the gold query". It searches with neighbor
   queries, "generated by modifying one aspect of the gold query"; a suite that tells every
   neighbor from the gold is likely to catch other wrong queries too. Harbor & Pine's second
   warehouse, `warehouse_alt`, is seeded so that each trap's naive query gives a different answer.

## Apply it to your repository

1. Take one question your agent answers, and write its gold query by hand.
2. Write two neighbor queries: drop one filter, and change one column. Run all three on your data.
3. If a neighbor returns the same result as the gold, your data cannot catch that mistake. Add rows
   that make the results differ, or a second, differently seeded database.
4. Compare with the trap-sensitivity tests in `platform/packs/datapilot_us/benchmark/`, where each
   item's `naive_sql` must differ from its `gold_sql` on both warehouses.
